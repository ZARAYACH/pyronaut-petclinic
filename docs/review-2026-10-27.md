## ETag behavior and Python adaptations

- `Vet` uses `@ETaggable` and `@GeneratedETag(function="SYS_ROW_ETAG")`. The application does not replace the generated optimistic-locking predicate with a Python equality check.
- The persisted assignment hash is SHA-256 of sorted, distinct persisted speciality IDs. Names do not participate. Renaming a speciality preserves the assignment ETag; changing assignments changes it.
- Create/read/update responses include the quoted `ETag` header and `Cache-Control: no-store`. Updates and deletes require `If-Match`; missing or blank values return 428, stale/weak values return 412, and successful deletion returns an empty 204.
- Link deletion/insertion and version-checked mutation share a transaction. Stale update/delete tests verify that rejected mutations leave names and links unchanged.
- The Python service explicitly enriches transient speciality collections and writes the join rows. This retains the earlier SDK-compatible mapping rather than introducing an unverified many-to-many cascade translation. Public DTOs include specialities and ETag, and exclude the private hash.
- H2 uses a small Java SQL-function adapter copied from the reference because H2 invokes a static JVM method. Application services, routes, DTOs and hash logic are Python. PostgreSQL/MySQL functions are managed by migrations; Oracle uses its native function.
- The reference now reads CRUD data through `VetService`. The port follows that fresh-read behavior. The older `ClinicService.find_all_vets` cache remains separately verified; HTML/CRUD JSON no longer serve its cached DTOs.
- Standard Micronaut `HttpStatusException` represents domain failures at the Python boundary. The verified HTTP status/message/path contracts match the new reference; Java checked-exception classes are not duplicated as a parallel hierarchy.

For an existing MySQL server with binary logging, arrange routine-creation privileges/settings or DBA provisioning before applying the ETag migration. The local development/CI container setting applies only to Test Resources.

## Remaining gaps and limits

1. **Sample-data lifecycle parity remains open (PORT-042/043).** The configuration switch gates vector loading but core SQL seed migrations still run independently of it. Disabled seeding, later enabling and persistent restart behavior are not established as matching the reference. This prevents a claim of complete source parity.
2. **Model/helper parity remains partial.** Python dataclasses and facade organization differ from Java records, identity equality and generated wither helpers. Public workflows and ETag mutation semantics are exercised; Java model APIs and generated-SQL snapshots have not been copied literally.
3. **Concurrent insertion of a previously absent catalog key remains unverified.** Six overlapping updates of an existing key pass. That does not prove every first-insert race.
4. **Browser behavior and distribution remain unverified.** Rendered form structure and source JavaScript assets are checked, but interactive maps, actual browser submission/reload flows, native builds and packaged startup away from the project root have not been exercised. The current static resource configuration uses `file:static`.
5. **Some source validation failure paths are defective or deliberately adapted (PORT-032).** The port returns useful validation errors rather than claiming parity with recorded reference 500 failures.
6. **Remote CI and production connection fallbacks have not been executed here.** Local tests use managed fixture databases and cached images. Passing local tests does not establish a remote workflow result.
7. **Oracle Deep Data Security is excluded by request.** No OAuth2/database authorization parity is claimed for those routes.

The encountered-problem log remains [porting-issues.md](porting-issues.md). No external issues, pull requests or remote pushes were created.
